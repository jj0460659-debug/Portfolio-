From 12 to 100 on Lighthouse

A performance and accessibility case study — taking a deliberately broken page and rebuilding it to score perfectly on every metric.

The Setup

To understand how much performance actually matters, I built two versions of the same simple page:

  • Before: a page that breaks every rule — blocking scripts, no meta tags, huge DOM, low-contrast text.
  • After: the same page rebuilt properly — clean HTML, inline CSS, semantic structure, accessible colors.

Then I measured both with Google PageSpeed Insights.

What was wrong:

  • Render-blocking scripts that froze the main thread for 2 seconds
  • 5,000 unnecessary DOM elements
  • Low-contrast text and no alt attributes on images
  • Missing meta tags, charset, viewport, and title
  • Mixed content warnings from HTTP resources on HTTPS
  • Deprecated HTML like <marquee> and <font>

What I changed:

  • Removed all render-blocking scripts and inlined critical CSS
  • Simplified the DOM from 5,000 elements to under 200
  • Added semantic HTML, alt text, and WCAG AA color contrast
  • Wrote complete meta tags — title, description, viewport, charset
  • Served everything over HTTPS with no mixed content
  • Used modern, standards-based HTML only

What I Learned

Performance isn't a checklist you run at the end. It's a series of small decisions you make while building — and each one has a cost.

The biggest surprise wasn't how slow the "before" page was — it was how easy the "after" page was to build once I knew the rules. Every fix was obvious in hindsight. The skill is in knowing them before you start.
